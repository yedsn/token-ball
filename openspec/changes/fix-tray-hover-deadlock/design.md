# Design

## Context

动机见 proposal.md。当前延迟悬浮任务在持有 `TrayHoverState` 的标准互斥锁时调用 `tray_bounds_for_event`；该函数通过窗口查询显示器。锁定的 `tauri-runtime-wry 2.11.4` 实现把查询发往事件循环并通过 `recv()` 等待。与此同时，托盘 Move/Enter/Leave 和点击处理也会获取该锁，形成可达的循环等待。

现场记录：2026-11-25 进程 PID 57712 为未响应，22:20 与 22:29 托盘更新出现 Windows 1460 超时。未取得故障调用栈，超时可能还涉及 Windows Shell，不能将上述路径视为本次故障的唯一已证实原因。

## Goals / Non-Goals

**Goals:**
- 共享锁只保护短时间的内存读写，不跨越 Tauri 查询、窗口操作或等待。
- 延迟请求取消和最终显示之间有明确的顺序，旧任务不能重新激活已取消的面板，也不能隐藏新请求的面板。
- 用可控交错测试验证锁释放与取消逻辑，用实际打包版验证 Windows 原生交互。

**Non-Goals:**
- 不更换 Tauri、互斥锁类型或后台运行时，不新增全局窗口管理架构。
- 不以定时重启、重建托盘或忽略超时掩盖故障，不调整现有交互时长。

## Decisions

### 1. 在锁外完成显示器与光标查询

延迟到期后，在锁内检查 generation 和 pending 状态并复制矩形、光标位置等必要数据，随后释放锁。显示器、窗口和光标查询在锁外执行；查询失败或光标已经离开时，仅在 generation 仍匹配时清理该请求。审核所有共享悬浮状态的锁作用域，遵守同样规则。

仅将 `lock()` 改为 `try_lock()` 会丢失点击或取消动作；改为异步锁也不能消除界面线程与窗口查询之间的依赖，因此不采用。

### 2. 最终显示在界面线程串行提交

延迟到期后将位置查询和最终处理一起投递到界面线程，减少一次跨线程往返。回调内先在锁内复制状态，释放锁完成查询，再检查 generation、pending 和抑制期限，释放锁执行显示；随后短暂加锁提交 shown 状态，失败时清理本请求。界面事件与最终提交按事件循环顺序执行，避免后台校验后、真正显示前插入一次取消。如果窗口操作发生重入并改变 generation，必须重新校验并避免旧任务对新请求执行隐藏或状态覆盖。

generation 继续承担取消标识，不新增第二套任务注册表。维持一个有效面板监控任务；自动隐藏通过界面线程重新检查归属后执行，监控任务使用 oneshot 等待结果，隐藏失败限速重试。键盘关闭和通用隐藏入口也将状态变更与窗口隐藏一起投递到界面线程。直接在后台查询后检查一次 generation 再显示仍有竞态，因此最终提交必须与界面事件串行。显示投递失败应结束匹配请求并记录错误，不保留永久 pending 状态。

### 3. 针对风险建立小范围回归验证

使用局部可注入查询或现有状态处理边界构造测试，不新增通用调度框架。通过通道或屏障暂停查询，使另一参与者取得状态锁并取消请求；断言不依赖查询先返回，并为测试等待设置超时，避免回归时测试永久挂起。另测取消后查询返回、旧任务晚于新请求返回、显示失败后的再次悬浮。

Windows 打包版按规范执行至少 100 轮交互，覆盖至少两次后台刷新，并记录构建版本、进程、步骤和日志时间段。重现率低不等于证明不存在问题，因此代码锁范围检查、可控交错测试与桌面验收均需完成。

## Risks / Trade-offs

- [现场原因未完全证实] → 修复已识别路径；若仍未响应，采集线程等待链或调用栈，再定位 Shell 或其他阻塞，不将超时直接归因于额度 API。
- [释放锁后状态可能变化] → 查询后在界面线程检查 generation；旧任务不修改新请求状态。
- [窗口显示期间重入或失败] → 操作前后检查归属，错误恢复保持可再次触发，不无条件隐藏其他请求的面板。
- [只在开发版验证会遗漏时序差异] → Windows release 打包版为必要验收，无法执行的项目明确标记待验证。
- [跨平台窗口调用行为不同] → 保持平台分支，编译与可用平台烟测记录实际范围，不声称未测试平台已通过。

## Migration Plan

无数据迁移。先完成回归测试和 Windows 打包验收，再按现有发布流程交付；本变更不自动发布。回滚为恢复本次代码修改并重新构建，用户配置无需更改。
